## Name -> address mapping rule
Every allow-list name carries the disassembly/COFF spelling: the upstream C identifier plus MinGW's one leading cdecl underscore (`blit` -> `_blit`; an already-underscored upstream name doubles up, `_win_hcursor` -> `__win_hcursor`). Stripping exactly one leading underscore and looking the result up as a DWARF `DW_AT_name` in the scope=all model resolved **all 126 names uniquely** (0 unresolved, 0 ambiguous) -- verified this run, not assumed; the generator aborts (exit 1) if that ever stops being true.

## Inline functions
**0 of the 100 allow-listed function names are upstream inline math** (`itofix`, `ftofix`, `fixtoi`, `fixtof`, `fixfloor`, `fixceil`, `fixmul`, `fixdiv`, `fixadd`, `fixsub`, ... -- checked against the well-known upstream `allegro/inline/*.inl` name set). This is the expected, mechanical consequence of how `tools_recon/lib_boundary_scan.py` built the census, not a gap: a `static inline` function compiles directly into the calling game CU's own `.text` (there is no separate callee, no call instruction, nothing for a call-edge scan to see), so it can never appear as a distinct name in `game_to_lib.callees` in the first place. If the game ever needs one of these (it apparently does not, per this scan), it would already be sitting inline in the relevant game CU's recovered bytes, not reachable through this binding layer at all.

## AL_INLINE vtable-dispatch macros
A second, DIFFERENT class of "inline function" from the fixed-point math above: `rectfill`/`putpixel`/... (`AL_INLINE_VTABLE_DISPATCH`, 23 curated names) are also `static inline` upstream, but their body is nothing more than `ASSERT(bmp)` plus one call through `bmp->vtable-><slot>(...)` with every argument passed through unchanged -- confirmed by hand-reading `allegro/inline/{gfx,draw}.inl` end to end (not scanned: there is no DWARF or call-edge evidence for an inline body's CONTENT, only for whether a name has an out-of-line callee at all). Because that body has no branch, rounding, or extra arithmetic to reproduce, it can be emitted as a macro with the same confidence as an ordinary VA binding, unlike a name such as `draw_sprite` (branches on color depth) that this generator deliberately leaves out of the curated list.

**23 emitted, 0 skipped** (collision with a reserved CRT/Windows identifier, an existing game-scope name, or an allow-list VA binding -- see LIB_BINDINGS_NOTES.md's own "Name collisions" counts for whether any of those applied this run). Emitted only into `pf_lib_bindings.h` (the carrier-active world) -- `allegro_api.h`'s declare-only branches need no equivalent: real upstream Allegro (the `ICYTOWER_UPSTREAM_ALLEGRO`-defined world) already provides these as its own inline macros, and no project using this generator currently compiles a file that calls one of these names in the third, neither-guard-defined declare-only world.

## AL_INLINE branching/math primitives
A third class, distinct from both sections above: `draw_sprite`, `rotate_sprite`, `fixtoi`, `ftofix` (curated in `AL_INLINE_BRANCHING_OR_MATH`) are also `static inline` upstream, but unlike the vtable-dispatch names their body has a REAL branch (`draw_sprite`: 8bpp vs. not) or REAL arithmetic (`rotate_sprite`'s own fixed-point centering; `fixtoi`/`ftofix`'s own fixed<->int/double conversions, no vtable call at all) that has to be reproduced, not just redirected. Hand-transcribed from `allegro/inline/draw.inl` and `allegro/inline/fmaths.inl` (both third_party/allegro-4.4.1 and -4.4.3.1 checked, identical), each emitted as a `static` helper function plus a `#ifndef`-guarded forwarding macro -- see this generator's `AL_INLINE_BRANCHING_OR_MATH` module comment for the exact upstream line numbers and the per-name reasoning.

**4 emitted, 0 skipped** (same three collision classes as the vtable-dispatch macros above). First closed for icytower_forged's own `src/icytower/draw_frame.c` (PROMOTIONS.md batch 10), which until now carried a private, `#ifndef`-guarded copy of exactly these four names -- this header's own `#define`s now win there automatically (force-included ahead of that file's own text), with no edit to that file.

## Name collisions
**CRT/Windows reserved-identifier collisions: 0.** Checked against the same conservative list `gen_bindings.py` uses (`RESERVED_CRT_WINDOWS_IDENTS`, reused here, not re-derived).

**Collisions with `pf_bindings.h`/`pf_bindings_src.h` (game-scope names, `carrier/gen/it_globals.h`/`it_funcs.h`): 0.** Every game-CU global/function name (156 + 242, `carrier/gen/interop_index.json` scope=game) was checked against all 126 allow-listed names; the sets are disjoint. If this ever produced a hit, the colliding game-scope name would need to move to `--exclude` on whichever generator binds it second, exactly like `gen_bindings.py`'s own `--exclude` handles a promoted function's name -- not automatic, because (as `BINDINGS_NOTES.md` already argues for the game-scope case) a plain-name `#define` cannot be silently renamed without breaking the reason it exists.

**Collisions within the allow-list itself (a function name equal to a global name, or a name repeated between the two lists): 0.**

## `--exclude`
Mirrors `gen_bindings.py --exclude`: an Allegro-family function about to be compiled natively into the carrier from `src/` (a game reimplementation of, say, `blit`) is passed on `--exclude` so its own name is left free in `pf_lib_bindings.h` instead of being redirected to its original address, the same self-redirection bug `gen_bindings.py`'s own docstring names for game-scope functions. This run used `--exclude (none)` (empty: no Allegro-family function is reimplemented in `src/` today).

## Standalone build swap
Inside the carrier: `pf_lib_bindings.h` is force-included (`/FI`), together with `pf_bindings.h` or `pf_bindings_src.h`, so `blit(...)`, `key[...]`, `screen`, `font` in `src/` resolve to `((PFN_LIB_<name>)VA)` / `(*(T*)VA)` at build time -- no `#include "allegro_api.h"` is even reached in a `src/` file that never writes it (and is a correctly-guarded no-op in one that does, via `ICYTOWER_BINDINGS_ACTIVE`).

Standalone (win32_pilot.md SS4 option (A), source-built Allegro 4.4.1): `src/` files that need Allegro symbols write `#include "allegro_api.h"` themselves, exactly as a real game would write `#include <allegro.h>`; the plain declarations in that file, not any macro, are what makes `blit(...)` etc. resolve. The swap is then a single-file change: delete `allegro_api.h`, and every `#include "allegro_api.h"` becomes `#include <allegro.h>` (plus `<loadpng.h>`/`<logg.h>` where `load_png`/`logg_load*` are used) -- nothing else in `src/` changes, because both worlds already agree on upstream names, upstream prototypes and upstream struct layouts (the DWARF recovery IS the 4.4.1 headers' own prototypes/layouts, not a second transcription of them). The one caveat already on record (`notes/library_boundary.md` SS4 option (A)): `_win_hcursor` has no public header of its own even upstream (`allegro/platform/aintwin.h`), so the standalone build still needs either that header or the 3-line platform helper already called out there.
