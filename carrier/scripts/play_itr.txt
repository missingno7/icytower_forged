# Triggering the actual "confirm and play the highlighted entry" action is

# workload" and src/icytower/INVIVO.md's same-named section for the full
# writeup. Left checked in (rather than deleted) because the navigation
# half is real, measured progress - a future pass can pick up exactly
# where this one left off:
#   - A real bug WAS found and fixed this pass: carrier/src/det.cpp's
#     deliver_due_input() hardcoded _handle_key_press's ASCII argument to 0
#     for every synthetic key (real Allegro's DirectInput driver only does
#     that for non-printable keys - ENTER/SPACE/ESC get a real ASCII value,
#     third_party/allegro-4.4.1/src/win/wkeybd.c). Fixed (ascii_for_
#     allegro_code()), verified to change nothing about ordinary gameplay
#     input (G1/human_test.txt gates still EQUAL), but did NOT by itself
#     make the confirm fire - _replay_selector's dispatch at 0x41d671 turns
#     out to be indexed purely by readkey()'s SCANCODE half, never the
#     ASCII half, so this specific mechanism was never the blocker for
#     DISPATCH (it may still matter elsewhere; the fix is correct
#     regardless).
#   - The likely REAL gate, found by disassembling _replay_selector in full
#     this pass (0x41d330-0x41d9dd): a local debounce counter
#     (-0x42c(%ebp), init 0x3e8=1000 at entry 0x41d330) decrements once per
#     loop iteration only while is_any(ctrl) is true (CTRL_ENTER included
#     in its mask, src/icytower/control.c) and not already exactly 0; the
#     MOMENT it hits exactly 0 while a button is held, every frame takes
#     the "movement" branch (0x41d3eb) and NEVER calls keypressed()/
#     readkey() until the button releases. This script's own key holds
#     (5 nav taps + a 360-tick KEY_ENTER hold entering the browser) are
#     very likely enough total held-iterations to drain the counter to 0
#     well before the second KEY_ENTER at T=2100. A tap (press+release,
#     not held) variant of the second KEY_ENTER was tried as the cheapest
#     test of this theory (from a scratch copy, not committed here) and
#     ALSO did not reach play() - so either the counter was already stuck
#     at 0 well before that point (consistent with the drain theory) or a
#     further, not-yet-identified factor is also in play. NOT root-caused
#     to a working fix within this pass's budget either.
#   - Candidates for a follow-up, in the order this pass would try them:
#     (a) re-run the whole sequence with a live single-step trace
#     (carrier's own --trace-window, milestone 9) watching the -0x42c
#     counter's actual value at T=2100, rather than inferring it from held-
#     duration arithmetic; (b) shorten EVERY hold in this script (nav taps
#     included) to the bare minimum press/release gap, keeping is_any()
#     true for as few loop iterations as possible before the confirm
#     attempt, so the counter has no chance to reach exactly 0 before then;
#     (c) an interaction with clear_keybuf() at replay_selector's own entry
#     (0x41d312) that this pass did not trace in detail (established that
#     it exists and runs once at entry, not that it interferes with a T=2100
#     event queued long after entry).
#
# Menu key sequence, found by disassembly (artifacts/disasm.txt) and
# notes/asset_census.md, not trial-and-error:
#   - main_menu (0x4bd380, asset_census.md): "Play Game / Instructions /
#     Profile / High Scores / Load Replay / Options / Exit". Item 0 ("Play
#     Game") is the default selection (same as scripts/newgame.txt).
#     MEASURED: 4x KEY_DOWN only reaches item 3 ("High Scores") - one tap is
#     evidently absorbed somewhere (assets/log.txt showed " high scores
#     selected" with only 4 taps); 5x KEY_DOWN reaches item 4 ("Load Replay")
#     reliably, confirmed repeatedly by "load replay selected" in the log.
#   - __mangled_main's own dispatch (artifacts/disasm.txt VA 0x4163f4-0x416403)
#     calls replay_selector(ctrl=0x5000c8) DIRECTLY when "Load Replay" is
#     confirmed - not a separate file-browser menu screen. --print-globals
#     num_itr_files (VA 0x4dd744, it_globals.h) read back 3 on this profile,
#     confirming the file list is populated, not empty.
#   - replay_selector (0x41d258) does NOT use the poll_control()/is_any()
#     path for confirmation, despite appearances - that path (0x41d3d1-
#     0x41d423) decrements a counter while a control key is held and is some
#     OTHER, still-unidentified mechanism (an idle/attract-mode timeout is
#     the working hypothesis, not confirmed). The REAL confirm path is
#     Allegro's buffered keypress queue: keypressed()/readkey() (0x41d416/
#     0x41d664/0x41d671), dispatched through a scancode-indexed jump table
#     at VA 0x4d7b18. Both KEY_ENTER(67) and KEY_SPACE(75) dispatch to
#     0x41d9dd, which is the "confirm the highlighted entry" handler (checks
#     a per-entry "is this a directory" byte at 0x50093c+cursor*24, then
#     calls play_menu_select()/sets the loop's own "done" flag at -0x444).
#     Our direct-injection _handle_key_press(keycode=0, scancode) SHOULD
#     populate this same buffer (real Allegro's _handle_key_press is the
#     canonical entry point regardless of caller) but was NOT observed to
#     trigger 0x41d9dd in this pass's runs (virtual T advanced into the tens
#     of thousands with zero safepoints, i.e. play() via run_demo() was
#     never reached) - NOT root-caused further within this pass's budget.
#     Candidates for a follow-up: (a) keycode=0 not being what readkey()'s
#     packing expects even though the jump table only inspects the scancode
#     half; (b) an interaction with clear_keybuf() at replay_selector's own
#     entry (0x41d312) that this pass did not trace; (c) the still-
#     unexplained poll_control/is_any counter path being a PRECONDITION

#     re-reading 0x41d40c-0x41d423 with a live single-step trace (carrier's

#     disassembly.
