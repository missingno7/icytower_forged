# The library boundary — can third-party code be a separate ownership boundary?

Date: 2026-09-07. Companion data: `artifacts/lib_boundary.json`, generated by
`tools_recon/lib_boundary_scan.py` (read-only over `artifacts/` + `assets/`).
Labels as in `win32_pilot.md`: KNOWN / INFERRED / HYPOTHESIS / TEMPORARY.

**Verdict up front (INFERRED, on the evidence below): yes.** Icy Tower's own
code touches its libraries only through the documented public API, in one
direction, at a countable surface: 100 distinct Allegro-family functions, 95
distinct DLL imports, 24 callback registrations, 26 library globals, and
**exactly one** genuine internal-symbol edge (`_win_hcursor`). No static table
mixes game and library function pointers; no library code writes any game
global. That is a header-level ABI, not an entangled one, so option **(C)** —
keep the embedded library inside the carrier, switch `src/` to upstream headers
at the standalone build — is the cleanest, and **(B)** (extract a DLL) is
unnecessary and specifically hard for reasons listed in §4.

## 4. The three options for the final standalone build

### (A) Link `src/` against source-built Allegro 4.4.1 + logg + libogg/vorbis, DLLs for libpng/zlib

This is the destination. Cost: build Allegro 4.4.1 with `ALLEGRO_STATICLINK`,
assembler off, DEBUGMODE off; build libogg 1.1.3 + libvorbis 1.2.0; vendor
`addons/loadpng` (as the game already does) and `addons/logg`. Everything the
game calls is a public name, so `src/*.c` compiles against stock
`<allegro.h>` / `<logg.h>` / `<loadpng.h>` with **no shim except one**:
`_win_hcursor`, which needs either `#include <allegro/platform/aintwin.h>` (as
the original build must have done) or a 3-line platform helper.

### (B) Extract the embedded Allegro into a DLL

Not recommended. Specific obstacles, each backed by the evidence above:

1. **Exported data, not just code.** 26 globals cross the boundary
   (`key[]` at 0x506988 is 101 sites; `screen`, `font`, `gfx_driver`, `joy`,
   `mouse_*`, `gui_*_color`, `allegro_errno`, `system_driver`, plus 13
   `_rgb_*_shift_*`). A DLL must export them as data, and MinGW-built
   `key[]`-style arrays would have to be reached through `__imp__` indirection
   — a source change on the *consumer* side, i.e. exactly the thing the
   boundary was supposed to avoid.
2. **`_driver_list` construction is link-time and constructor-time.**
   `__gfx_driver_list` / `__system_driver_list` / `__timer_driver_list` etc. are
   `.data` tables built by `drvlist.c`, and `almngw32.h` defines
   `ALLEGRO_USE_CONSTRUCTOR`; `__digi_driver_list` and `__midi_driver_list` are
   `.bss` filled at runtime. Splitting the image changes when those run.
3. **`allegro_init()` registers `atexit` in the *caller's* CRT.** The call site
   at `0x415f57` passes `0x401000` = the game's own `_atexit`. In a DLL split
   the library's teardown would be sequenced by the wrong CRT.
4. **CRT sharing.** The whole image is one `msvcrt.dll` heap today
   (`malloc/free` are direct imports); `pack_fopen`/`load_datafile` hand
   pointers back and forth. Two CRTs (or msvcrt vs. ucrt) means cross-heap
   `free`. The carrier already redirects the malloc family to one arena at
   `0x20000000` precisely because it is a single control point.
5. **`BITMAP->vtable` is a pointer into the C blitters.** Every `BITMAP` the
   game holds carries `___linear_vtable{8,15,16,24,32}` addresses; a DLL split
   makes those addresses live in another module, which breaks snapshot/restore
   identity and the "state stays address-backed" contract of §7a.
6. **Packfile password state.** `packfile_password` is called 7 times and sets a
   library-global password used by `pack_fopen`/`load_datafile`; it must stay on
   the same side as the packfile reads.
7. **logg static state + DirectX COM objects.** logg holds its stream state in
   library globals, and the DirectDraw/DirectSound/DirectInput COM interfaces
   are owned by `src/win/wdd*.c` / `wdsound.c` / `wdsinput.c`. Moving them
   across a module boundary buys nothing (they are already in-process) and adds
   an identity layer the snapshot model explicitly defers
   (`win32_pilot.md` §6, §10).
8. **Threads.** Allegro creates its timer, window and DirectInput threads
   itself; the carrier already virtualises them by *entry address*
   (`_beginthread` wrapper). A DLL boundary would move those addresses.

### (C) Embedded library stays inside the carrier; `src/` targets the public header ABI — **chosen**

The boundary is a **header-level ABI**, and the evidence says the game only
uses it that way: 100 public Allegro-family functions, 25 public globals, 24
public registration calls, 1 internal edge. Therefore:

- **Now**: `src/` calls `blit(...)`, `key[...]`, `install_int(...)` by their
  plain public names. Inside the carrier those names resolve to the embedded
  library's addresses through a *generated* extension of `pf_bindings.h`
  (§6). No DLL, no export table, no CRT split, no vtable relocation.
- **Later**: the same `src/*.c`, byte-for-byte, compiles against upstream
  `<allegro.h>` and links a source-built Allegro. The `#define` layer simply
  disappears — the same two-worlds trick already proven for game globals in
  `carrier/gen/BINDINGS_NOTES.md`.
- The library is **never lifted, never promoted, never diffed function by
  function**. Its correctness is asserted by the replay digest, not by a
  per-function oracle.

## 5. Verification plan

### 5.1 "game src + embedded Allegro" vs "game src + source-built Allegro"

The comparison domain is already correct and already generated: the **151
game-owned globals** (`carrier/gen/gen_game_globals.py`), per tick, sha256.
`notes/living_record.md` records why raw `.data`+`.bss` never converges — ~20–30
Allegro/CRT/DirectX globals hold host object identities. That finding is exactly
what makes a library swap testable: the verdict domain is defined by *ownership*
(DWARF CU), so replacing everything outside it must leave the digest EQUAL.

```
same .itr / --input-script workload, same seed, --det
  ├── carrier: src/ + unrecovered game bytes + EMBEDDED Allegro   (oracle)
  └── standalone: src/ + recovered game code + SOURCE-BUILT Allegro
compare per tick: sha256 of the 151 game-owned globals
first difference → (tick, global name, byte offset)
```

Because the second build has no guest image, the digest must be computed over
the port's *own* storage (`src/icytower/state.c` and successors) with the same
field order — i.e. the digest spec becomes a generated manifest
(name, type, size) rather than an address list. That manifest is the artefact
that makes the two worlds comparable, and it should be generated from the same
`interop_index.json` that produced `game_globals.inc`.

### 5.2 What a plain-source replay driver needs

1. **Key injection at tick boundaries.** Do not drive DirectInput. Call
   Allegro's `simulate_keypress` (already a public function the game itself
   calls 6×) or write `key[]` directly at the tick boundary, from the main
   thread, exactly as the carrier's `--input=script` does. This also fixes
   divergence 002 by construction (`living_record.md`: real events arrive at
   sub-tick times, replay injects at boundaries, so the recorded tick
   coordinate is ±1).
2. **Deterministic timer.** Do not let Allegro's timer thread drive
   `cycle_counter`. Register the same two `install_int` callbacks
   (`fps_counter` 1000 ms, `cycle_counter` 20 ms) against a **virtual clock**
   stepped from the replay loop, and make `rest()` advance that clock. This is
   the standalone twin of the carrier's `_handle_timer_tick` virtualisation.
3. **RNG pinning.** `rand`/`srand` are msvcrt imports today. Standalone, ship
   the msvcrt LCG (`x = x*214013+2531011; return (x>>16)&0x7fff`) in the port so
   the tower layout does not depend on the host CRT.
4. **x87 control word.** Set `CW = 0x037F` (bare `FNINIT`) at startup, or the
   physics will differ from the oracle — `artifacts/lift_x87_finding.md`.
5. **Driver pinning.** Force the GDI (`GDIB`) or a headless gfx driver and
   `digi_none` / `midi_none` via `set_config_file` / `override_config_file`, so
   the replay never depends on DirectDraw or DirectSound availability.
6. **Tick digest** over the manifest from 5.1.

### 5.3 Observable differences to expect first (HYPOTHESIS, ordered)

1. **Timer semantics.** `timer_win32_high_perf` vs. `timer_win32_low_perf`
   selection, and whether the source build's `install_int` rounds 20 ms the same
   way. Symptom: the catch-up branch in `play()` sees a different tick backlog.
2. **Input backend.** DirectInput scancodes vs. injected Allegro codes
   (`key_dinput_handle_scancode` takes raw DIK codes, not Allegro codes —
   `living_record.md`). Symptom: wrong key indices in `key[]`.
3. **Colour conversion / blitters.** If the source build enables the i386
   assembler blitters, `blit`/`stretch_blit`/`makecol` results can differ at the
   pixel level even when the logic digest matches. This is why "C-only" is a
   **must-reproduce** setting.
4. **Mixer.** `digi_dsoundmix` vs. `digi_waveout` vs. `digi_none` changes voice
   IDs (`gameMusicVoiceID`, `checkMusicVoiceID` are game globals) and
   `voice_get_position` results, which the game reads. Pin the digi driver.
5. **Packfile/datafile.** `packfile_password` handling and LZSS decode must be
   identical or `data/*.dat` will not load.

### 5.4 Evidence required before a region is declared safely externalizable

A region (CU family, or a single CU) may be marked THIRD-PARTY-EXTERNAL only
when all five hold:

| # | criterion | status today |
|---|---|---|
| i | **CU provenance matches upstream file names.** Every CU path in the region maps 1:1 onto a file in the upstream tarball at the identified version. | **met** for Allegro (106 CUs under `C:\Lib\allegro4\`), logg (1), loadpng (3 vendored), libogg (2), libvorbis+vorbisfile (20). Not met for `csv.c`, `httpget.c`. |
| ii | **Function bodies match upstream at instruction/line-table granularity for a sample.** Propose: compile 6 upstream files (`src/color.c`, `src/blit.c`, `src/timer.c`, `src/c/cblit32.c`, `addons/logg/logg.c`, `framing.c`) with GCC 4.4.1 at the inferred flags and compare (a) function count and order per CU, (b) per-function byte size, (c) the DWARF line table's line-number set. Byte-identity is not required; *shape* identity is. | **not done** — this is the one open item |
| iii | **No game→internal-symbol edges.** | **met with one exception**: `_win_hcursor` (2 stores). The `loadpng` internals (`_color_load_depth`, `_fixup_loaded_bitmap`) are inside the vendored addon, which upstream also calls, so they cross no boundary that the addon's own source does not. |
| iv | **No game-visible behaviour depends on private build configuration beyond what a config file reproduces.** | **partially met**: driver *lists* are link-time, but driver *selection* is config-driven (`set_config_file` at `0x40f03a`). The C-only blitter choice is **not** config-reproducible and must be a build flag. |
| v | **The replay digest stays EQUAL after rebinding.** | **not done** — needs 5.1 |

## 6. Migration path

### NOW — carrier: `src/` + unrecovered game bytes + embedded libraries

Already true. `carrier/gen/pf_bindings.h` binds **156 game globals + 242 game
functions** to their original addresses; scope is `game` only
(`interop_index.json.scope == "game"`). Verified: **0** of the 100 Allegro-family
API names appear in `pf_bindings.h`. That is correct today only because the two
promoted functions (`update_frame`, `is_solid`) are pure logic with no library
calls.

### NEXT — the library-call layer (the concrete gap)

The moment a promoted `src/` function calls `blit()` or reads `key[]`, the
carrier build has no symbol for it. Required work, all generated:

1. **Extend the binding generator to a `library` scope.** Re-run
   `gen_interop.py --scope all` and emit `carrier/gen/pf_lib_bindings.h` with
   one `#define` per name in the boundary inventory — the 100 Allegro-family
   functions, the 25 public globals, and (separately, flagged) `_win_hcursor`.
   The names are already 1:1 with upstream: the COFF/DWARF symbols are
   `_blit`, `_textout_ex`, `_install_int`, `_key`, `_screen`, … i.e. the exact
   public API spellings, so `src/` writes `blit(...)` and nothing else.
2. **Do not bind the libraries' internals.** The generator must refuse any name
   outside the inventory, so a future `src/` file cannot silently acquire a
   dependency on `_color_load_depth` or a vorbis symbol. `artifacts/
   lib_boundary.json` is the allow-list.
3. **Types.** `src/icytower/game_types.h` must gain the handful of Allegro
   types that cross (`BITMAP`, `SAMPLE`, `MIDI`, `FONT`, `DATAFILE`, `RGB`,
   `PALETTE`, `PACKFILE`). Standalone these come from `<allegro.h>`; inside the
   carrier from the DWARF-recovered layouts — with the known caveats in
   `carrier/gen/INTEROP_NOTES.md` (`BITMAP.line` is a flexible array, so
   `BITMAP` is opaque-tailed; 6 cross-CU size conflicts, all in DirectInput /
   `BITMAPINFOHEADER` types the game never touches).
4. **Extend the purity gate.** `scripts/check_native_layer.py` should accept
   `#include <allegro.h>` (and `logg.h`, `loadpng.h`) as legitimate in `src/`,
   because that include *is* the boundary, while still banning carrier headers
   and guest addresses.

### THEN — standalone build against upstream + replay driver

Build Allegro 4.4.1 (static, no-asm, no-DEBUGMODE) + logg + libogg 1.1.3 +
libvorbis 1.2.0; vendor `addons/loadpng`; keep `libpng3.dll`/`zlib1.dll` as
DLLs; add the replay driver of §5.2; run the §5.1 comparison.

### Items that can remain untouched **forever** (never lifted, never promoted)

| region | bytes | why |
|---|---:|---|
| Allegro core + C blitters + win drivers + misc | 466 683 | upstream source exists at the exact version; reached only through 98 public entry points |
| logg addon | 2 041 | upstream; reached through 2 entry points |
| libvorbis + libvorbisfile + libogg | 121 232 | upstream; **zero** direct game edges |
| mingw CRT + libgcc + import thunks | 35 851 | replaced by whatever CRT the standalone build uses |
| vendored `loadpng.c`/`savepng.c`/`regpng.c` | 4 260 | upstream addon; re-vendor the same files |
| vendored `strptime.c`, `timecompat.c` | 2 270 | replace with the host CRT or re-vendor |
| **total** | **632 337 B = 84.2 % of `.text`** | |

The recovery target is therefore **116 113 B / 217 functions / 18 CUs**, minus
whatever `csv.c` (671 B) and `httpget.c` (2 327 B) turn out to be.

### Items that must be handled explicitly

1. **The 24 callback registrations** (§3b). Each one is a game function whose
   *signature and calling convention* the library fixes. When `install_timers`,
   `init_game`, `register_png_*` or `update_file_list` is promoted, its callback
   arguments must be real `src/` functions, and the carrier's binding table must
   stop redirecting those callees to their original addresses.
2. **`cycle_counter` / `fps_counter`.** These two `install_int` callbacks are the
   determinism seam. Promoting them means the virtual clock must drive `src/`
   code, not guest bytes — coordinate with `carrier/src/det.cpp`.
3. **`_win_hcursor`** — the single internal edge. Either include
   `allegro/platform/aintwin.h` (matching the original build) or wrap it in one
   platform helper. It must be named in the allow-list, never silently bound.
4. **The vendored addon copies.** Decide once: re-vendor upstream `loadpng` (and
   accept its two internal Allegro calls, as upstream does), or re-express PNG
   loading over the public API. Do not "recover" `really_load_png` /
   `really_save_png` as game logic — 3 936 B of third-party code.
5. **Driver selection and config.** `set_config_file` (`0x40f03a`) plus
   `tower.cfg` decide the gfx/digi/midi drivers. The standalone replay driver
   must pin them, and the frame oracle (milestone 9a) depends on being able to
   force `GDIB`.
6. **`csv.c` / `httpget.c` provenance.** Until resolved, treat as game-owned;
   `httpget.c` is also the ad-fetch thread, already slated for suppression under
   `--det`.
