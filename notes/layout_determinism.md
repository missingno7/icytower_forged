# Icy Tower 1.5.1 -- what the tower/platform layout depends on

Scope: `assets/icytower15.exe`. Claims tagged **KNOWN** (seen directly in
`artifacts/disasm.txt`/`dwarf_info.txt`, address given) or **INFERRED**
(reasoned from KNOWN facts). Full call-site table: `artifacts/rand_call_sites.json`.

## 1. Every srand()/rand() call site (KNOWN, exhaustive grep of `disasm.txt`)

**`srand` (target `_srand` @ 0x4badc8), exactly 3 call sites, all main.c:**
- `init_game` **0x40ef53**: `time(NULL)`(0x40ef4b)->`srand()`. Startup-only,
  before any menu/game exists.
- `new_game` **0x40e0a0**: `time(NULL)`(0x40e098)->`srand()`. Executed
  **only** when global `demo` (`Treplay*` @ 0x4dd250) is NULL at entry.
- `new_game` **0x40de24**: `srand(eax)` -- the real per-game reseed,
  reached by both new_game control paths (traced instruction-by-instruction,
  no live register write to `eax` on the path between them and this call):
  - `demo==NULL` path: `eax` = the `rand()` result from 0x40e0a5, itself
    generated by the just-executed time-seed. `jmp 0x40e0bb->0x40de0c`
    falls straight through into this instruction.
  - `demo!=NULL` path (**KNOWN, correction to the prior simplified model**):
    `eax` = `demo->random_seed` (`Treplay+0xa4`), reloaded at **0x40dddc**
    from the *existing* Treplay struct -- i.e. **every `new_game()` call
    after the first one in a process run reuses the currently-loaded
    replay's stored seed instead of drawing a fresh time seed.** `demo` is
    created once (`create_replay` @ 0x40e01a, demo==NULL path only) and is
    never reset to NULL afterward (exhaustive grep of all `0x4dd250`
    read/write sites); it is only reassigned by `load_replay()` calls in
    `init_game`(0x40eb73/0x40f0d4, `-replay`/continue-file only),
    `do_replay_menu`(0x4117cc), `run_demo`(0x415e37). **Effect:** repeated
    "Play Again" in one process reuses whichever game/replay's seed is
    currently loaded. Doesn't weaken the carrier conclusion below (a saved
    `.itr`'s `random_seed` is still authoritative either way).

**`rand` (target `_rand` @ 0x4bad18), exactly 18 static call sites** (full
per-site table in `rand_call_sites.json`):
- `add_floor` (3 sites, 0x416956/0x4169bc/0x4169d3) -- **the only live
  gameplay consumer**, see §2.
- `new_game` (0x40dcba, 0x40e0a5) -- 0x40e0a5 produces the real seed
  (stored to `rec_seed` global 0x4fe7a8 and `Treplay+0xa4` @ 0x40e0b5,
  0x40dda5-0x40dddc); 0x40dcba reseeds the *separate* `new_rand` PRNG (§3),
  consuming from the libc stream's pre-reseed state.
- `init_game` (0x40f1ed, 0x40f61f) -- 0x40f1ed picks a `rand()%1000`
  table-slot index (global 0x4fe518, INFERRED an ASLR-style indirection
  index for a per-run pointer table, used only as an array index at 100+
  sites, never combined arithmetically into floor data); 0x40f61f reseeds
  `new_rand` again (loading-screen time). Both run at process startup,
  **before** `new_game()`'s per-game reseed, so neither affects layout.
- `fldads_get_random_ad` (0x403b36, ad-spot selection) -- reachable only
  via `load_new_ad_image`(0x415eac)<-`__mangled_main`(0x4160ee), called
  once when returning to the **main menu**, never from inside `play()`.
- `create_post` (beta.c, 3 sites) and `scroll_star_field`/
  `init_star_field` (stars.c, 7 sites) -- **KNOWN dead code**: their
  callers (`load_garbled_data`/`load_plain_data`; `scroll_star_field`/
  `init_star_field` themselves) have **zero** call sites anywhere in the
  binary, direct or indirect. The live star-scroller is
  `restart_scroller`(0x41f0d0), which has no `rand()` call at all.

**Does `init_game`'s `srand` (0x40ef53) affect gameplay?** No layout
effect: consumed by 0x40f1ed (memory-index selection) and 0x40f61f
(`new_rand` seed) before `new_game()` runs; `new_game()` re-seeds libc
`rand()` again at 0x40de24 before `add_floor` runs.

## 2. `add_floor` (0x4167dc-0x416a3c, `void add_floor(Tmap *m)`, DWARF-named)

**KNOWN inputs, read directly in the function body:**
- `m->room[31].level` (Tfloor.level, offset 0xc of Tfloor, `it_types.h`) --
  a counter *inside the Tmap struct itself*, incremented by exactly 1 on
  every reachable return path. This is the floor index `k`: it equals the
  number of `add_floor()` calls issued so far, independent of wall clock.
- `get_demo()->0x8c` / `->0x90` = `Treplay.floor_shrink` / `.floor_size` --
  fixed per-game difficulty settings, copied into `Treplay` once at
  `new_game()` (0x40e04b-0x40e081, from globals 0x4fe538/3c/40/44/48).
- `floor_size_modifiers[5]` (VA 0x4bdb60, DWARF-confirmed, map.c static
  const table) indexed by `floor_size`.
- 3x `rand()` (0x416956/0x4169bc/0x4169d3, see below).

**NOT read anywhere in `add_floor`** (checked the full disassembly range):
`cycle_count`/tick counter 0x506938, `logic_count`, QueryPerformanceCounter/
`clock()`/`time()`, player x/y/state, `Treplay.data`/record stream.

**rand() calls per invocation: 0, 1, or 2 -- data-dependent, but the
"which case" decision is itself a pure function of `(level, floor_shrink,
floor_size)`, never of a prior rand() *value*:**
| condition (all on the running `level` counter / fixed settings) | rand() calls |
|---|---|
| `level%250==0` (level<=5004) or `level%2500==0` | 0 (deterministic checkpoint floor) |
| `level%5!=0` (non-checkpoint) | 0 (deterministic filler floor, tiles=-1) |
| `level%5==0`, `floor_shrink==0` | 2 (0x4169bc, then 0x416956) |
| `level%5==0`, `floor_shrink!=0`, new level<=3000 | 2 (0x4169d3, then 0x416956) |
| `level%5==0`, `floor_shrink!=0`, new level>3000 | 1 (0x416956 only) |
No branch after any of the 3 rand() calls feeds back into whether another
rand() call happens -- traced the FPU compare at 0x4169ef-0x416a0e (looks
data-dependent) and confirmed it branches on the *level*-derived float, not
the just-drawn rand() value.

**Callers (KNOWN):** `new_game` 0x40de4b -- `reset_map()` then a fixed
`for(i=0;i<30;i++) add_floor()` building the initial 30 floors. `play`
0x4120e0 -- gated by comparing the player's climbed-height marker against
the highest-floor-generated marker (0x4f8e18); called **on demand** as the
player crosses into unrevealed territory, at most once per tick. So *when*
floor k is generated depends on player timing/skill, *what* it contains
does not (see below).

**Is floor k a pure function of (seed, k)? YES (INFERRED from the KNOWN
facts above), given fixed difficulty settings for the game:** the branch
structure (case table above) depends only on `k` and the constant
`floor_shrink`/`floor_size`; the RNG stream `add_floor` draws from is libc
`rand()`, which nothing else touches during gameplay (§1: ad selection
runs at the menu only; `create_post`/stars.c are dead code). So the
number of rand() calls consumed by floors `1..k-1` is itself deterministic
in `k-1` and the fixed settings -- **no interleaving with any other rand()
consumer occurs during gameplay, and none is possible under different
frame timing**, because the only thing that varies with player
timing/skill is *when* `add_floor` is called, never *how many* times it's
been called for a given floor index.

## 3. The second PRNG: `new_rand`/`new_srand` (KNOWN, does not affect layout)

`new_rand()`(0x406984)/`new_srand()`(0x406a04) is a **separate** FP
multiplicative-congruential PRNG, state = the `double` at global VA
**0x4ff108** -- independent of libc's internal `rand()` state.
`new_srand()` has **zero** call sites; its state is seeded only by the two
libc-`rand()`-derived stores at 0x40dccf/0x40f63a (§1). 18 `new_rand()`
call sites reviewed (`rand_call_sites.json`): all cosmetic -- particle
x/velocity/color (`create_particle`/`update_particle`), reward/sound
triggers, blit jitter in `draw_frame`, random taunt-text selection (`play`
0x415bcd/0x415c19, string table 0x4bc0c0), menu effects. **None write
into `Tfloor`/`Tmap` fields.** Its own state word means timing-dependent
calls during gameplay cannot perturb `add_floor`'s libc-`rand()` stream.

## 4. Conclusion table

| Layout input | Value | Reproducible from `.itr` alone? |
|---|---|---|
| RNG seed | `Treplay.random_seed` (offset 0xa4), time-derived only for the *first* new_game() of a process, reused thereafter | Yes -- saved verbatim in every `.itr` |
| Floor index `k` | Count of `add_floor()` calls so far (self-incrementing `Tmap.room[31].level`) | Yes -- deterministic given the seed and difficulty settings |
| Difficulty tables | `floor_shrink`/`floor_size`/`start_speed`/`speed_increase`/`gravity` (Treplay offsets 0x8c-0x9c), constant per game | Yes -- saved in the same `.itr` header |
| `floor_size_modifiers[5]` | Static const table, VA 0x4bdb60 | N/A (binary-constant, not a variable) |
| Other rand() consumers interleaved during gameplay | None live (ad selection menu-only; create_post/stars.c dead; new_rand disjoint) | N/A |
| Tick counter / QPC / clock / time | Never read by `add_floor` | N/A |

**Definitive statement:** a carrier needs exactly **one integer**,
`Treplay.random_seed`, plus the five difficulty-setting fields already
stored alongside it in the same header (`floor_shrink`, `floor_size`,
`start_speed`, `speed_increase`, `gravity`) to regenerate the entire tower
layout bit-for-bit, for any floor index, independent of input timing or
frame count. **No interleaving order needs to be recorded** -- the only
rand() consumer running during gameplay is `add_floor` itself, and its
per-floor call count is deterministic in the floor index and the
(also-recorded) difficulty settings, not in anything external.
